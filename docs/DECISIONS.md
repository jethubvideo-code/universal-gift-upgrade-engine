# Решения

Формат: вопрос → выбранный безопасный вариант → почему → как это настройка.

## 0.4 — Транспорт исполнения апгрейда

**Решение (владелец, 2026-10-04): Вариант B — Bot API Business connection.**
Бот действует от имени управляемого бизнес-аккаунта; пользователь сам
связывает бота в настройках Telegram Business → Bots и выдаёт права
(посмотреть подарки и Stars, передать/апгрейдить подарки, передать Stars),
отзываются там же в один клик. Никакой MTProto user-сессии, никаких SMS/2FA
через чат, единственный секрет — токен бота. Код Варианта A остаётся в
`src/telegram/mtproto-client.js` и соседях как неактивный путь
(`TRANSPORT=mtproto`).

**Что проверено сразу после решения**: все методы Варианта B
(`getBusinessConnection`, `getBusinessAccountGifts`,
`getBusinessAccountStarBalance`, `upgradeGift`, объекты `BusinessBotRights`,
`OwnedGiftRegular`, `Gift`) сверены с официальной документацией Bot API
10.3 — детали в `docs/API_VERIFICATION.md`.

## Репозиторий / место работы

**Вопрос**: спека говорила работать внутри `gifttracker-bot`.
**Решение**: владелец явно переопределил — отдельный репозиторий
`universal-gift-upgrade-engine`. `gifttracker-bot` используется только как
read-only внешний источник публичного сигнала (HTTPS GET его
`docs/gifts.json`), никогда не изменяется этим проектом.
**Статус**: подтверждено владельцем напрямую в чате.

## 0.5 — Политика коллизий (несколько пользователей → один (collection, N))

**Решение по умолчанию**: **исполнять все независимо** (не одна попытка на
коллекцию/номер). Причина: Telegram сам арбитр — кто успел, тот получил
номер; система не может справедливо выбрать «одного» пользователя без
произвола. UI/уведомления обязаны честно предупреждать о конкуренции (раздел
10 текста согласия уже это требует). Это уже так работает в коде (каждый
`target` — независимая запись, `TargetIndex.byNumber` возвращает ВСЕХ, кто
метит в тот же номер, `HotTargetEngine.onCollectionUpdate` переводит в
HOT_TARGET и запускает `handleHot` для каждого независимо).
**Настройка**: `COLLISION_POLICY=all-independent` (единственное значение
сейчас; `single-attempt` зарезервировано как возможное будущее расширение,
не реализовано — делать его сейчас было бы угадыванием несуществующего
требования).

## 0.6 — Стек и хостинг

**БД**: файловое хранилище (`FileStore`, JSON per-table в `data/state/`),
коммитится обратно воркфлоу монитора. Атомарность — через `store.tx()`
(синхронная секция) и `LockManager` (TTL + fencing token) поверх него.
**Почему не Redis/Postgres**: владелец работает с телефона без сервера;
GitHub Actions — единственная бесплатная вычислительная среда без настройки
инфраструктуры. SQLite (`better-sqlite3`) оставлен как `optionalDependency`
для будущего self-hosted режима (раздел «self-hosted» в
`docs/DEPLOYMENT.md`), не как основной путь.
**Клиентская библиотека Telegram**: GramJS (`telegram` npm, optional
dependency) — наиболее зрелая MTProto-библиотека для Node.js, активно
поддерживается, используется в множестве production user-session ботов.
**Хостинг постоянного worker**: НЕ выбран как основной путь — см. 0.4,
GitHub-only режим покрывает мониторинг и бот; реальное исполнение апгрейда
(money-sensitive) обсуждается в 0.4 именно потому, что «постоянный worker»
имеет смысл только если выбран Вариант A с MTProto-сессией, которую
рискованно держать на эфемерном раннере.

## 0.7 — Скан секретов

## 0.8 — SLO (предложение, не окончательное — зависит от 0.4)

Реалистичные ожидания с учётом found в 0.3(b): без официального источника
`upgradedCount`, detection latency зависит от частоты обновления внешнего
публичного сигнала (т.е. от gifttracker-bot/t.me, не от нас). Предлагаю:

| Этап | Цель (p50) | Цель (p95) | Примечание |
|---|---|---|---|
| Detection (наш сигнал → HOT_TARGET) | < 200 ms | < 1 s | измерено: ~18 ms на 10k целей в памяти (`test/perf/`), реальный потолок = частота внешнего сигнала, не наш код |
| Verification (7.5, запрос к Telegram) | TBD | TBD | нельзя измерить без Варианта 0.4 |
| Execution (от UPGRADE_READY до отправки) | TBD | TBD | нельзя измерить без Варианта 0.4 |

Окончательные числа для Verification/Execution будут в
`docs/TEST_REPORT.md` после Фазы 4/5, когда появится реальный (или dry-run)
вызов — обещать их сейчас значило бы придумывать маркетинговые цифры, что
запрещено правилом 3.8.

## 0.9 — Speed Mode: пересмотр 0.4 (владелец, 2026-10-04)

**Контекст**: Business-бот (0.4) требовал Premium + привязку в Telegram
Business, которая так и не завершилась (0 business-апдейтов за весь период
поллинга), и в любом случае не даёт задержки <1с — цикл GitHub Actions раз в
5-15 минут принципиально не годится для ловли конкретного номера.

**Решение**: вернуться к Варианту A (прямой MTProto от пользовательской
сессии владельца), заготовленному ещё в v1.0, но не активированному. Business
API/бот снят с критического пути (и так ничего не делал — привязка не
завершилась); код не удалён, оставлен неактивным (`TRANSPORT=botapi` остаётся
default, чтобы не сломать текущий GitHub Actions цикл — новый постоянный
worker явно включает `TRANSPORT=mtproto`).

**Что сделано (Фаза A)**: исправлены параметры `payments.upgradeStarGift` /
`inputInvoiceStarGiftUpgrade` (поле `stargift`, не `saved_gift` — было
неверно в коде v1.0, сверено с core.telegram.org Layer 225), добавлен
`inputSavedStarGiftUser` конструктор, добавлен второй шаг оплаты
`payments.sendStarsForm` (отсутствовал), добавлена проба
`payments.getUniqueStarGift` для детекта окна. Добавлены режимы
`test`/`dry-run`/`live` (section 6) — `dry-run` по умолчанию, апгрейд не
отправляется. Скрипты: одноразовый вход (`npm run login`), замеры
(`npm run dryrun`), локальный синтетический T_fire-бенчмарк (`npm run
bench:fire`, см. реальные цифры в TEST_REPORT.md).

**Находки, важные для владельца**:
1. `availability_issued` (поле из спеки для счётчика апгрейдов) НЕ
   подтверждено в текущей схеме (`starGift`, Layer 225, core.telegram.org) —
   там только `availability_remains`/`availability_total` (остаток обычного
   тиража). Детект окна поэтому строится ТОЛЬКО на подтверждённом
   `payments.getUniqueStarGift`, не на гипотетическом счётчике.
2. GramJS (`telegram` npm, 2.26.22) при установке помечен npm как
   **archived / no longer maintained**, с указанием на форк `teleproto` как
   активно поддерживаемый. Используется, т.к. это всё ещё последняя
   опубликованная версия и API совместим, но это риск на будущее (если
   Telegram поменяет Layer ещё раз, патча от GramJS может не быть) — стоит
   рассмотреть переход на `teleproto` отдельной задачей.

**Не сделано (Фаза B/C, следующие шаги)**: горячий путь (память-только,
атомарный флаг «выстрелено», подготовка формы заранее, zero-await на пути
выстрела), разделы Mini App «Мои подарки» / «Зафиксировать номер»,
WebSocket/SSE статус, деплой без перекрытия. Начинается после того, как
владелец пришлёт результат `npm run dryrun` с реального сервера.
